4. ГРАФ ЗАДАЧ, КЛЮЧ КЕША, ПОВТОРЫ
----------------------------------
Prefect-flow release_flow (flow.py):
  prepare-input (кешируемая) -> resolve-candidate -> gate-decision ->
  publish-release. Между задачами передаются небольшие описания: пути, id,
  хеши, outcome. Веса и тензоры как результаты задач не передаются. Стадия
  получения артефакта читает ГОТОВЫЙ training run ДЗ 6+7 — чтение результата,
  не повторное обучение (повторный sweep не выполнялся).

Ключ кеша стадии подготовки — release.cache_key: SHA-256 канонического JSON
{data_sha256, config}, где config = {tokenizer_revision, template_sha256,
max_length, code_revision}. Файл и mtime не участвуют. Результат сохраняется
Prefect (persist_result, LocalFileSystem внутри рабочего каталога,
.lab-flow/prefect-results/) и читается после завершения процесса.

Где возможен повтор: подготовка (кеш по содержимому), публикация ТОГО ЖЕ
выпуска (already-published без записи). Где запрещён: публикация другого
выпуска всегда создаёт ровно одно новое событие; повторная оценка требуется
при изменении модели/данных/условий генерации.

Политика повторов: в пути выпуска нет сетевых операций — артефакт читается
из локального snapshot HF-кеша, поэтому ограниченный retry для временной
сетевой ошибки не требуется; если появится удалённое хранилище, повторять
можно только транзиентные ошибки транспорта. Неверная схема отчёта,
несовместимые веса (хеш файлов) и отказ по качеству (quality_gate) —
ValueError без повторов: повтор не исправляет (процесс завершается кодом 2,
указатель и журнал событий не меняются).

6. GATE: СВЯЗАННЫЙ ОТЧЁТ, ОТРИЦАТЕЛЬНЫЕ ПРОВЕРКИ
-------------------------------------------------
release-report.json создаётся обвязкой, а не руками:
  - фикстурный стенд: validate_release требует статус complete, настоящий
    boolean passed, evaluation_run_id, совпадение model_id и четырёх хешей с
    манифестом, конечные accuracy/format_rate в [0,1];
  - реальный выпуск: make_real_release.py вызывает quality_gate ДЗ 6+7 на
    замороженных отчётах (хеши в artifacts/real/source/source-manifest.json),
    кандидат REFUSED; baseline публикуется с release-report-baseline.json,
    где passed=true означает «полная оценка завершена без ошибок генерации,
    отчёт связан с манифестом, версия удерживается после отказа кандидата» —
    это решение процесса (retain), а не результат сравнения baseline с самим
    собой. PASS из фикстур никогда не подставляется в реальный выпуск:
    фикстуры живут в .lab-* (synthetic=true), реальный выпуск — только из
    отчетов ДЗ 6+7 с их исходными хешами.
Отрицательные проверки (все падают с ValueError, указатель побайтно не меняется):
  неполный отчёт (status=running, passed='false' строкой) —
  tests.test_integration::test_incomplete_report_refused + лог
  d2-publish.log (SHA-256 accepted.json до/после); чужой отчёт A для B —
  test_report_binds_to_its_model; отказ по качеству (passed=false) —
  test_reject_report_keeps_bytes; NaN/Inf/чужие хеши/runtime со свежим хешем —
  публичные тесты (test_invalid_metric_rejected и др.); ошибка записи —
  публичный test_failed_atomic_replace_preserves_previous_bytes (mock os.replace).
Почему PASS из фикстуры не оценка модели: фикстуры синтетические
(STUB ONLY, synthetic=true), их метрики (0.8/1.0) не измерены на данных;
реальная связь training run -> eval -> решение -> загруженная модель:
  run 40fb010a… (адаптер) -> candidate-eval.json -> quality_gate REFUSE ->
  удержание baseline (Qwen3-0.6B @ c1899de…) -> загружена в API (см. раздел 7).

7. API: РЕАЛЬНЫЙ СЕРВИС
------------------------
FastAPI (service.py): GET /health (живость), GET /ready (200 только после
проверки хешей артефакта, загрузки весов и прогревочного вызова; до этого
503), GET /debug (тестовый маршрут: loaded/advertised, calls, warmup),
POST /generate.
Сервис читает принятый манифест (artifacts/real/accepted.json), сверяет
SHA-256 всех закрепленных файлов артефакта (1.5 ГБ) до загрузки и загружает
Qwen3-0.6B @ c1899de… с dtype float32 и параметрами генерации из
manifest.runtime — теми же условиями, что при оценке. Случайный локальный
конфиг не используется.
Лимиты: max_new_tokens 1..32 (зафиксирован протоколом, сообщение об ошибке
называет диапазон), prompt <= 2048 символов, тело <= 64 КБ, параллельные
вычисления ограничены (semaphore=1 для реальных весов; очередь честно видна
в поле queue_seconds). Изменение лимита на запрос наследует допуск только
внутри диапазона 1..32; произвольные настройки генерации API не принимает.
Ответ: answer, output_tokens (фактическое число), model_id (фактически
загруженный), runtime_sha256, request_id, queue_seconds, generation_seconds.
Реальный smoke (evidence/after/real-smoke.log): ready 200 с model_id и
runtime_sha256; реальный ответ Qwen3-0.6B — 32 токена, generation ~3.2 с;
max_new_tokens=100000 -> 400 «поддерживается диапазон 1..32», calls не
вырос. Неверный запрос без вызова backend — tests.test_integration::
test_invalid_requests_do_not_reach_backend (5 неверных -> 0 вызовов).
Версия в памяти: до перезапуска API отвечает загруженной версией, даже если
accepted.json сменился; после перезапуска загружается согласованный выпуск
— опыт A -> B -> A: evidence/after/aba-experience.log (STUB-версии;
реальный smoke — отдельная проверка, фикстуры не выдаются за модель).

8. ЗАМЕР (часть D)
-------------------
Условия: реальный сервис Qwen3-0.6B float32 CPU, прогрев 1 запрос, один и
тот же набор из 8 ASCII-запросов (choices A–D), max_new_tokens=32 для всех,
backend semaphore=1 (последовательные веса). Каждая попытка в
measurements/bench-*.jsonl и *.csv (id, режим, статус, клиентская задержка,
queue/generation seconds, model_id, output_tokens; ошибок не было — поле
error осталось null, из журнала ничего не удалялось).

  mode     n  ok/err  package_s  req/s   avg_lat_s  max_lat_s  avg_gen_s  tokens
  conc1    8  8/0     21.356     0.375   2.669      2.791      2.658      256
  conc2    8  8/0     23.669     0.338   5.527      6.031      2.958      256

Объяснение: в conc2 клиентская задержка удвоилась (avg 5.5 c), при этом
суммарное время пакета почти не изменилось (21.4 -> 23.7 c): каждый второй
запрос ждал освобождения весов в очереди (queue_seconds 2.8–3.2 c у 7 из 8),
а не считался дольше (avg_gen 2.66 -> 2.96 c — разброс прогрева CPU).
Ожидание (очередь) и вычисление (prefill+decode) разделены полями
queue_seconds и generation_seconds. Prefill — обработка промпта до первого
токена (короткий промпт -> доля мала), decode — авторегрессия 32 токенов,
KV-cache растет линейно по длине контекста; при едином JSON-ответе измеряется
полная задержка — TTFT/ITL отдельно не выделяются и не выдумываются.
Ограничения: n=8 — на такой выборке устойчивый p95 не вычисляется и не
заявляется; последовательный CPU-Transformers не доказывает скорость
SGLang/vLLM (тот не измерялся: непрерывная батчировка иpaged KV-cache —
другая архитектура обслуживания); замер — не бенчмарк железа.

9. STUB-ОПЫТ И ВОССТАНОВЛЕНИЕ ПОСЛЕ СБОЯ
-----------------------------------------
A -> B -> A (evidence/after/aba-experience.log):
  1) сервис на A: pointer=A, loaded=A, ответ=A;
  2) опубликован B в другом процессе, БЕЗ перезапуска: pointer=B, loaded=A,
     ответ рапортует A (фактически загруженную версию);
  3) управляемый перезапуск: loaded=B, ответ=B;
  4) откат к ранее принятой A (run --report report-A.json) + перезапуск:
     pointer=A, loaded=A, ответ=A — подтвержден ответом.
Журнал событий: ровно 2 записи (B и A, по одной на выпуск).
Повтор выпуска после сбоя между указателем и журналом:
  tests.test_integration::test_crash_between_pointer_and_journal_recovers —
  указатель заменен, журнал пуст; повтор восстанавливает согласованность:
  ровно одно событие, повторный запуск не дублирует (outcome=recovered).
Реальный smoke выполняется отдельно от STUB-опытов (см. раздел 7).
